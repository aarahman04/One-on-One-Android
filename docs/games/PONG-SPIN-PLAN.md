## Findings from emulator play and code (2026-10-25)

1. **Sideways overhit.** Production (main, 2.0.12) aims `x = .5 + direction*.658*(.7+.3f)`;
   a sideways swipe (`direction = ±1`) aims at `x ≈ -.16 / 1.16`, outside the table. The
   unmerged 2026-10-24 branch saturates inside the table but deliberately keeps an
   `OVERHIT` term (+.3 for fast near-sideways swipes) that still sends the ball off the side.
2. **No real spin.** "spin" is only a fixed sideways endpoint drift (curve). There is no
   topspin/backspin, no bounce kick, and the receiver is unaffected by the incoming ball.
3. **The demo opponent always returns a neutral, centred ball**, so receiving varied
   shots cannot be tested on the emulator.
4. Points should be lost by **missing** the ball, never by a legal swipe direction.

## Rules (shared spec: backend `pongPhysics.ts`/`pong.ts`, Kotlin `PongPhysics`/`DemoPong`/`PongClient`)

Notation: stroke gives `direction`, `f` (forward, [-.5,1]), `p` (power, [0,1]), `vx`
(sideways finger speed, world x, widths/s, signed) and `vy` (finger speed toward the
opponent, widths/s, signed). `smooth(v,a,b)` is the existing smoothstep. `T+ = max(T,0)`,
`T- = max(-T,0)`.

### Spin captured at contact
- Sidespin `S = clamp(vx / 8, -1, 1)` (world x sign; + curves toward +x).
- Top/back `T = smooth(vy, 4, 10)` when `vy > 0`, else `T = -smooth(-vy, .5, 4)`.
  Fast forward flick = topspin, pulling back / chopping = backspin, still bat = none.

### Incoming spin (ball spin at the moment of contact, after its bounce)
- `activity = clamp(hypot(vx, vy) / 6, 0, 1)`, `passive = 1 - activity`.
- Lateral raw (signed): `Lraw = sign(direction)*raw + .15*inS*passive`, `raw` as today.
- `L = LATERAL_MAX * tanh(Lraw / LATERAL_MAX)` with `LATERAL_MAX = .42`. **Remove `OVERHIT`.**
  Landing x = `.5 + L` ∈ [.08, .92] for every stroke: no swipe leaves the side.
- Depth: `f_eff = clamp(f + passive*(.2*inT+ - .35*inT-), -.35, 1)` (final; plan -.5) replaces `f` in the
  target y formula (topspin blocked passively goes long, backspin passively goes short).

### Flight
- Bend share (part of L delivered as in-air curve via endpoint drift): `.15 + .35*|S|`
  (was a fixed .4). Drift still lands exactly at `x = .5 + L`.
- Arc height scale `k = 1 - .3*T+ + .1*T-` applied to the two control-point heights
  (P1.z, P2.z); P3.z stays `-6/12.16`. `landingWeights(z, k)` uses
  `height(u) = (1-u)^3 z + 3(1-u)u*k*h - u^3 h`.
- Duration `flightDuration(p) * (1 + .15*T-)` (final: the plan's `-.1*T+` topspin term tuned to 0).

### Bounce
- Sideways kick: `vx += .25 * S * |vy|`, then the existing 45° clamp.
- Reach multiplier `m = 1 + .35*T+ - .45*T-`, pace multiplier `q = 1 + .1*T+ - .35*T-` (final; plan .25)
  (`bounce(vx, vy, vz, pace, m, q)`; the 2 s cap rule is unchanged). The shot pace counts at most
  `BOUNCE_PACE_MAX = 2.2` widths/s: `duration = ground*scale / max(min(pace, 2.2)*.9*q, 1e-6)`.
- Bounce control-point heights scale `1 - .35*T+` (topspin skids low, backspin sits up).
- After the bounce the ball keeps `S *= .6`, `T *= .5` (that is the receiver's `inS/inT`).
- Point reset clears spin.

### Frame (additive)
- New `sp: [S, T]` (4 dp): the ball's current spin. Existing `spin`/`drift` keep their meaning.
- Android validates `sp` (optional, size 2, finite, clamp to [-1,1]); web ignores it.

### Fairness and robustness constraints (tests must prove)
Fuzz every combination: swipe angle 0..345° step 15°; finger speed {0, .5, 2, 4, 6, 8, 10,
14, 20} widths/s; contact x {-.2, .1, .5, .9, 1.2}; contact y two depths behind the hitter's
end; contact z {-.03, .05, .2, .45}; incoming `inS, inT` ∈ {-1, 0, 1}. For each:
- all numbers finite, duration in [.1, 2];
- first table crossing lands **inside the table on the opponent's half**;
- the receiver can reach the ball (existing `pongFairness` reachability model: .2 s
  reaction, 6 widths/s bat, legal racket region) with a return window ≥ 250 ms.
If a coefficient above breaks a constraint, tune that coefficient (smallest change) and
record the final value in the API contract and this file. Backend and Kotlin must match
to 1e-9 via a shared golden fixture generated by the backend.

## Android-only work
- Mirror the physics exactly (`PongPhysics.launchArc` with `inS, inT`; `DemoPong`).
- `PongClient` decodes `sp` and passes the ball's incoming spin into its own return
  prediction so prediction matches the server.
- Spin visuals in `PongUi`: a mark on the ball that rolls along the flight for top/back
  (direction by sign) and orbits for sidespin, speed ∝ |spin|; trail tint warm for
  topspin, cool for backspin. (A per-hit "Topspin/Backspin/Sidespin" label was tried and
  removed on owner feedback: the trail is enough.) The play area is clipped to its
  rounded yellow box so balls past the end line never draw over the controls.
- Hint under the table: one line teaching flick forward = topspin, pull back = backspin,
  sideways = curve.
- Demo opponent (debug only) varies its returns: neutral, topspin drive, backspin push,
  sidespin left/right, placement left/right, so receiving spin is testable on the emulator.

## Final tuned values (2026-10-25, from the fuzz)

flight duration topspin term `0` (plan -.1), bounce pace `q = 1 + .1*T+ - .35*T-` (plan .25),
